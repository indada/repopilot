# RepoPilot 1.6.0

RepoPilot 1.6.0 makes verification-driven software iteration available as a persistent, self-hosted service. GitHub events wake the controller; current API evidence, explicit policy and independent tests determine whether a candidate can advance. Codex proposes tests and repairs while the controller owns budgets, recovery and publication.

## What's new

- **Persistent iteration service**: `serve` combines optional signed GitHub Webhooks with polling compensation for eligible Issues, owned PR follow-up and explicitly enabled PR review.
- **Durable event queue**: atomic delivery deduplication, coalescing by Issue/PR, fresh-input revalidation, bounded retries, dead-event inspection and interrupted-work recovery. Events received during execution remain queued.
- **Daily budgets and circuit controls**: persistent UTC call, token and task allowances cover every Codex role and parallel execution fork. Unknown usage retains its reservation; `service pause` interrupts active work and `service resume` preserves consumed allowances.
- **Progress feedback**: optional GitHub comments reuse an authenticated author-and-marker pair, retain a local outbox and recover ambiguous writes. Progress comments cannot become repair acceptance criteria.
- **Evidence-driven candidate queue**: trusted, labeled Issues must demonstrate missing behavior with stable independent tests before manual approval or explicitly configured automatic approval. Other signals retain evidence without gaining code-change authority.
- **Fixed-case strategy replay**: pinned evaluation suites compare matching cases across profiles; optional verification and cost gates defer new automatic intake while preserving already-approved recovery.
- **Controlled parallel DAG execution**: resource-aware waves, deterministic file ownership, conflict detection and bounded serial replay combine candidate snapshots only after cumulative tests pass. Accepted siblings and merge decisions retain durable audit evidence.

Existing repository rule checks, goal planning, feature implementation, Issue repair, PR maintenance, Node/Vitest/pytest/Go/JUnit evidence, post-merge tracking, crash recovery and preview verification remain available. Automatic merging and production deployment remain outside the controller's authority.

## Downloads

Portable packages include Node.js 22, production dependencies, launchers, examples and documentation for:

- Linux x64 and ARM64 (`.tar.gz`)
- Windows x64 (`.zip`)
- macOS Intel and Apple Silicon (`.tar.gz`)

Extract the complete directory and verify its archive against `SHA256SUMS.txt`. Run `./repopilot` on Linux/macOS or `.\repopilot.cmd` on Windows. Git and Docker with Linux containers are external prerequisites. The packages are command-line tools and are not code-signed or notarized.

The matching Agent image is `ghcr.io/indada/repopilot-agent:1.6.0` for Linux amd64/arm64. Model calls require `OPENAI_API_KEY`; GitHub credentials remain in the controller. Repair and publication stay disabled in the supplied examples.

## Upgrade and service setup

Stop the old controller and extract 1.6.0 into a separate directory. Preserve your configuration, data directory, reports, goals and snapshots. Update `agent.image` to `ghcr.io/indada/repopilot-agent:1.6.0`, pull the image, then run `--version` and `doctor`. Agent/runner or execution-policy changes invalidate existing goal configuration identity; preserve old evidence and create a new goal when needed.

**Issue queue behavior changes from 1.5.0:** `iterate` first reproduces the requested behavior and defaults to waiting for manual approval. Existing queue configuration without `autoApprove` therefore stops after reproduction. Only explicitly setting `iteration.queue.autoApprove=true` permits a reproduced candidate to continue automatically. Editing an Issue cannot grant its existing goal a fresh execution budget.

To use the service, adapt `examples/service.json`, configure the runner and Agent, and add the trusted `service` section. Polling works without public ingress. Optional Webhooks require a controller-held random secret and a reachable HTTPS endpoint in front of the local listener. Progress comments require separate opt-in and a GitHub user token with comment permissions.

```sh
./repopilot serve --config config.local.json
./repopilot service status --config config.local.json
./repopilot service pause --config config.local.json
./repopilot service resume --config config.local.json
```

Use `.\repopilot.cmd` instead on Windows. See the [service guide](https://github.com/indada/repopilot/blob/v1.6.0/docs/SERVICE.md), [candidate iteration guide](https://github.com/indada/repopilot/blob/v1.6.0/docs/CANDIDATE-ITERATION.md), [parallel collaboration guide](https://github.com/indada/repopilot/blob/v1.6.0/docs/MULTI-AGENT-COLLABORATION.md) and [portable quickstart](https://github.com/indada/repopilot/blob/v1.6.0/docs/QUICKSTART.md), also included in each package.

## 中文说明

RepoPilot 1.6.0 将“GitHub 输入 → 测试复现 → 受控修复 → 独立验证 → 修复 PR”推进为可常驻运行的本地服务。新增 Webhook 验签、轮询补偿、持久化事件队列、每日预算、熔断与人工暂停/恢复、幂等进度评论；同时打包证据驱动候选队列、固定用例策略评测，以及 DAG 节点受控并行、冲突重试和快照安全合并。

本版本提供 Linux x64/ARM64、Windows x64、macOS Intel/Apple Silicon 五个平台便携包，以及匹配的 1.6.0 Agent 镜像。升级请保留配置与数据目录。旧 Issue 队列默认改为复现后等待人工批准；自动批准、进度评论和修复发布均需明确配置，程序不会自行合并或上线。
